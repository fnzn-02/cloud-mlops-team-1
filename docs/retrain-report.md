# 로그 기반 재학습 보고서 (학습 전/후 비교)

## 1. 결론

- 서비스 로그(CloudWatch)에서 모은 1,690행을 학습 자료에 더해 **같은 입력·같은 모델로 재학습**했고, 새 모델을 EC2에 자동 배포해 측정했다.
- **평가용 전체 1,690행에서 MAE는 85.11 → 83.97(−1.14)이지만 95% 신뢰구간이 −3.32 ~ +1.01로 0을 포함한다. 개선이라고 말할 수 없다(차이 없음).**
- 배포본을 평가용 500행으로 측정하면 84.96 → 80.99(−3.97, 신뢰구간 −7.71 ~ −0.24)로 개선처럼 보인다. 그러나 같은 모델을 나머지 1,190행에서 보면 85.08 → 85.12(+0.04)로 **변화가 없어서, 500행의 개선은 표본이 만든 우연**이다(5절).
- 새 모델은 악화가 아니므로 반영(promote)했지만, 반영 근거는 "더 많은 자료로 다시 학습했고 나빠지지 않았다"이지 "성능이 좋아졌다"가 아니다.

**걸러 낸 기준** (`src/logs_to_training.py` 맨 위 설명): 예측 기록이 없으면 입력을 모른다 / 실제값이 충돌하거나 범위 밖이면 제외 / **평가용 시간 칸과 겹치면 제외**(겹치면 전후 비교가 무너진다) / 이미 학습에 쓴 칸은 제외(가중치만 커진다) / 검증용 칸은 원본 실제값과 같을 때만 사용.

**운영 중이던 모델의 오차** (피드백이 있는 1,694건)
- 전체 MAE **90.90**. 원본 검증용 MAE(README의 90.84)와 같아서, 로그 연결·전처리가 올바르게 동작했다는 확인이 된다.
- 시간대별 MAE: 새벽 48.6 / 오전 86.6 / 오후 99.1 / **저녁 128.1**
- 편향(예측 − 실제): 비 옴 −29.2(적게 예측), 공휴일 +30.2(많게 예측), 저녁 +13.4. 즉 약한 곳은 **저녁·비·공휴일**이다.
- 로그의 입력 분포는 학습 자료와 거의 같다(시간대 비율 24~26%, 기온 평균 12.5 / 12.9, 비 온 시간 6.8% / 5.9%). 새로운 상황이 아니라 **이미 학습한 분포의 자료**를 다시 넣은 것이다.

## 5. 배포 후 비교 (2번 측정과 같은 입력)

`results/deployed-eval-before.json` / `after.json`, 화면 캡처 `docs/retrain-before-web.jpg` / `retrain-after-web.jpg`. 배포된 서비스 API(`POST /predict`)에 평가용 500행(seed 7)을 보내 측정했다. 피드백은 보내지 않았다.

| | 재학습 전 (main `bef1076`) | 재학습 후 (브랜치 `3452d17`) |
|---|---|---|
| `model_version` | `d7a782f5853d` | `33353f858e24` |
| 500행 MAE | 84.96 | 80.99 |
| 오차가 실제값의 10% 안인 비율 | 49.4% | 50.4% |
| 데모 입력 2018-06-15 18시 25°C 습도 50 강수 0 | 3,266대 | 3,330대 |
| API 11개 케이스 | 모두 정상 | 모두 정상 |

- 데모 입력의 **실제값은 2,891대**(평가용 행)이다. 이 한 건은 오차가 375에서 439로 **오히려 커졌다.** 한 건으로 결론을 내리면 안 되지만, 캡처만 보면 "좋아졌다"는 인상을 줄 수 있어 함께 적는다.
- 화면의 "평균 오차 약 85대" 문구는 코드에 고정된 값이라 재학습해도 바뀌지 않는다.

**500행의 −3.97이 믿을 만한가? 아니다.**

| 평가용 부분 | 행 수 | MAE 이전 → 이후 | 차이 | 95% 신뢰구간 |
|---|---|---|---|---|
| 전체 | 1,690 | 85.11 → 83.97 | −1.14 | −3.32 ~ +1.01 |
| 배포 측정에 쓴 500행 | 500 | 85.19 → 81.24 | −3.96 | −7.67 ~ −0.14 |
| 나머지 | 1,190 | 85.08 → 85.12 | **+0.04** | −2.67 ~ +2.74 |

- 같은 모델을 같은 평가용 안의 다른 행에서 보면 개선이 사라진다. 평가용에서 무작위로 500행을 5,000번 뽑으면 차이는 −4.63 ~ +2.33 사이에서 움직이고, −3.97 이하는 약 6%뿐이다. **500행은 운 좋게 뽑힌 표본**이고, 판단은 더 큰 표본(1,690행)에 맞춰야 한다.
- (API 값과 오프라인 값이 조금 다른 것은 API가 예측을 정수로 반올림해서 돌려주기 때문이다. 84.96 vs 85.19, 80.99 vs 81.24.)
- 측정에 쓴 500행도 평가용의 일부라서 두 번째 독립 증거가 아니다.

## 6. 왜 거의 달라지지 않았나 (해석 — 가설이며 검증하지 않았다)

- 로그 행은 **학습 자료와 같은 분포**(3절)에서 왔고, 오차가 큰 곳(저녁·비·공휴일)을 겨냥한 자료가 아니다. 같은 분포의 자료를 25% 더 넣어도 이 모델에서는 더 배울 것이 적었을 가능성이 있다.
- 오차의 상당 부분은 자료 양보다 **입력 정보의 한계**(날씨 관측값 7개, 지난 시간의 대여 수·이벤트 등 없음)에서 오는 것일 수 있다. 이를 확인하려면 학습 자료 크기를 늘려 가며 평가 오차가 어떻게 변하는지(학습 곡선)를 봐야 한다. 아직 하지 않았다.

## 7. 한계

- **피드백은 시뮬레이션이다.** 팀원이 실제로 서비스를 쓴 것이 아니라 한 사람이 원본의 검증용 행을 되풀이해 보냈다. 실제 이용자 피드백이라면 값이 틀리거나 빠지거나 특정 사용자에게 치우칠 수 있다. 이 보고서는 그 어려움을 검증하지 못했다.
- 재학습 자료가 전부 검증용 행이라서 이번 재학습은 사실상 **학습+검증(80%)으로 다시 학습**한 것과 같다. 로그를 거쳤다는 점만 다르다.
- 평가용은 원본의 랜덤 20%이고 시간 순서 분할이 아니다. 미래 예측 성능과는 다르다(README 한계 참고).
- 입력 고르기를 다시 하지 않았으므로 더 나은 입력 조합이 있는지는 모른다.
- 팀원 PR 리뷰와 실제 이용자 로그가 없는 상태의 결과이다.

## 8. 다음에 해 볼 것

1. 저녁·비·공휴일처럼 약한 곳의 자료를 겨냥해 모으거나, 그 구간에 맞는 입력(예: 강수 구간, 공휴일 전후)을 추가해 입력 조합을 다시 고른다.
2. 학습 자료 크기별 평가 오차(학습 곡선)로 "자료를 더 모으면 도움이 되는가"를 먼저 확인한다.
3. 시간 순서로 나눈 평가(앞 달 학습, 뒷 달 평가)와 날씨 예보값 입력으로 실제 사용 상황에 가깝게 평가한다.
4. 실제 팀원이 서비스를 쓰고 `/feedback`을 보내도록 해서 진짜 로그의 품질 문제(빈 값, 오입력, 치우침)를 확인한다.

## 9. 다시 실행하는 법

```sh
# 1) CloudShell에서 CloudWatch 로그를 받는다 (scripts/fetch_cloudwatch_logs.py 또는 aws logs filter-log-events)
# 2) 전처리: 로그 → 재학습용 자료와 분석 보고서
python src/logs_to_training.py <로그 파일> --out-clean data/processed/log-training.csv --report results/log-analysis.json
# 3) 재학습·전후 비교 (--promote: 악화가 아니면 models/model.joblib 교체)
python src/retrain.py --promote
# 4) 배포본 측정 (전·후 같은 --seed)
python src/eval_deployed.py --url http://<서버>:8000 --label after --n 500 --out results/deployed-eval-after.json
# 로그가 부족하면 팀원이 각자 (시뮬레이션)
python src/replay_feedback.py --url http://<서버>:8000 --who <이름> --n 100 --seed <팀원별로 다르게>
```
