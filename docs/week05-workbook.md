# 5주차 학습지 · 계산하고 영상의 결과 설명하기

설치나 명령 실행 없이 문서로 작성할 수 있습니다. 종이는 초안에 사용하고 최종 결과는 저장소 파일로 정리해 PR(변경 사항 반영 요청)로 제출합니다. 영상 관찰을 직접 실행한 것으로 기록하지 않습니다.

## 0. 먼저 앱의 사용 장면을 이해하기

학생은 학습 앱의 문제 목록에서 풀 문제를 고릅니다. 문항은 문제 하나이고, 풀이시간은 문제를 연 순간부터 답을 제출할 때까지 흐른 시간입니다. 앱에는 문제를 고르는 순간 예상 시간을 표시하려 합니다.

![한 번의 풀이가 기록되는 과정](concept-images/attempt-timeline.webp)

- 문제를 고를 때 이번에 실제로 걸릴 시간을 알 수 있나요? 알 수 없음, 아직 풀지 않았기 때문에
- 실제 시간은 언제 기록할 수 있나요? 답을 제출한 뒤, 문제를 연 시각과 제출 시각의 차이로 기록
- 아직 풀지 않은 문제의 시간을 예상하려면 어떤 과거 기록을 이용할 수 있나요? 이미 끝난 풀이들의 문제 정보(글자 수·선택지 수)와 실제 풀이시간

비교할 설명: 고를 때는 아직 모릅니다. 제출한 뒤 시작·종료 시각의 차이를 기록합니다. 이미 끝난 풀이의 문제 정보와 실제 시간을 이용해 계산 방법을 정할 수 있습니다.

## 1. 같은 문항에서 오차 비교

실제 시간은 가12초·나18초·다35초입니다. 모든 문항에18초를 답하는 기준선의 각 오차와 MAE(평균절대오차)를 계산하세요.

- 각 오차: 가 6초 / 나 0초 / 다 17초. 합계 23초 ÷ 3건 = 평균 약 7,67초.
- 설명용 식이12·22·32초를 답했다면 각 오차 0 / 4 / 3초, MAE 약 2.33초.
- 이 세 문항에서 더 작은 오차인 방법은 설명용 식입니다. 새 문항에서도 더 좋다고 단정할 수 없는 이유는 세 문항은 이미 본 자료이고 개수도 적어서, 처음 보는 문항에서 따로 확인해야 하기 때문입니다.
- +10초와−10초의 오차가 서로 취소되면 안 되는 이유는 두 번 모두 10초씩 틀렸는데 평균이 0이 되어 전혀 틀리지 않은 것처럼 보이기 때문입니다.

## 2. 학습·평가 원리

- 학습 / 검증 / 평가 자료가 각각 맡는 역할: 계산 방법(계수)을 정함 / 여러 방법·설정 중 하나를 고름 / 고른 방법의 성능을 마지막에 한 번 확인.
- 평가 정답을 보고 계속 방법을 바꾸면 생기는 문제: 방법이 평가 자료에 맞춰져서, 새 자료에서의 성능보다 점수가 좋게 나온다. 평가 자료가 더 이상 "처음 보는 자료"가 아니게 됨.
- 예측할 순간에는 알 수 없는 정보를 입력에 넣은 사례를 하나 쓰세요: 자전거 대여 수 예측에 그 시간의 실제 관측 강수량을 넣은 것. 예측하는 시점에는 예보값만 알 수 있음.
- (200−150)÷50= 1입니다. 변환 기준까지 모델과 함께 저장해야 하는 이유: 예측할 때도 학습 때와 같은 기준(평균 150, 간격 50)으로 바꿔야 모델이 배운 숫자 범위와 맞기 때문이다. 기준이 없거나 달라지면 같은 입력도 다른 값으로 변환되어 예측이 틀어짐.
- 같은 입력의 예측이 재시작 전후 같다는 것과 정확하다는 것의 차이: 다는 것은 같은 모델을 제대로 다시 읽었다는 뜻(재현성)이다. 정확하다는 것은 예측이 실제 정답과 가깝다는 뜻이다. 틀린 값을 매번 똑같이 낼 수도 있음.

## 3. 로컬 영상 관찰

시청 전에 예상 칸을 적고, 시청 후 관찰과 비교합니다.

| 조건 | 예상 결과 | 영상에서 본 결과와 고칠 대상 |
|---|---|---|
| 숫자 글자 수·선택지 수 | 200, 예상 시간(초) | 200, 약 31.2초(글자 205, 선택지 2). |
| 글자 수가 문자열 | 입력 오류 | 422, 글자 수 항목 오류. 고칠 대상: 입력 |
| 모델 파일을 읽을 수 없음 | 서버 오류 | 모델 준비 실패 응답. 고칠 대상: 모델 경로·파일 |
| 모델 경로를 복구한 뒤 정상 입력 | 200, 이전과 같은 값 | 200, 약 31.2초로 복구 전과 같음 |

200과 예상31.2초를 받았을 때 실제 시간이50초라면 차이는 18.8초입니다. 200만으로 품질을 알 수 없는 이유는 200은 요청을 처리해서 답을 돌려줬다는 뜻일 뿐, 그 답이 실제와 가까운지는 알려 주지 않기 때문입니다.

## 4. 배치 영상 관찰

- 입력 요청 수 5건. 수정 전 정상 4건·실패 1건.
- 바꾼 것은 모델인가요, 입력인가요? 입력. 구체적으로 실패한 행의 잘못된 값를 규칙에 맞는 숫자 값로 바꿨습니다.
- 수정 후 정상 5건·실패 0건. 실패행을 삭제하는 것과 수정하는 것의 차이: 삭제하면 4건 중 4건 성공처럼 보이지만 원래 요청 1건은 처리되지 않은 채 사라짐. 수정하면 원래 5건을 모두 처리.
- 배치 작업이 완료되어도 행별 결과를 읽어야 하는 이유: 작업 완료는 전체 실행이 끝났다는 뜻이지 모든 행이 성공했다는 뜻이 아니다. 어떤 행이 왜 실패했는지는 행별 결과에만 있음.

## 5. 팀 설계 한 장

팀명: 1팀
예측하려는 시점: 해당 시간의 자전거 공급·재배치를 정하기
입력과 단위: 날짜(주말 여부·월 계산용), 시간(0~23시), 기온(°C), 습도(%), 강수량(mm), 공휴일 여부(0/1). 서비스에서는 날씨 예보값을 입력
예상 결과와 단위: 서울 전체 공공자전거의 한 시간 대여 수 (대)
실제 정답을 얻는 방법: 그 시간이 끝난 뒤 대여 기록에서 실제 대여 수를 집계
단순 비교 기준: 모든 시간에 학습 데이터의 평균 대여 수를 답하기 (MAE 519.6대)
평가 자료를 나누는 방법: 8,448행을 학습 80% / 평가 20%(1,690행)로 랜덤 분할 (random_state=42). 평가 자료는 학습에 쓰지 않음. 현재 결과 MAE 93.7대(기준선 대비 82% 개선)
함수·HTTP(웹 요청·응답 통신 규약)·배치 중 필요한 방식과 이유: HTTP 요청별 응답. 운영자가 날짜·날씨를 바꿔 가며 바로 확인해야 하기 때문
아직 확인하지 못한 것: 
- 예보값을 입력했을 때의 성능 (학습에는 관측값을 씀)
- 시간 순서로 나눴을 때의 성능 (랜덤 분할이라 같은 달이 학습·평가에 섞임)
- 검증 자료 없이 평가 자료 점수를 보고 입력·모델을 골랐음 → 학습/검증/평가 3분할로 다시 확인 필요

| 상황 | 예상 응답 | 원인과 고칠 곳 | 수정 후 확인할 증거 |
|---|---|---|---|
| 정상 입력 | 200 + 예상 대여 수(대) | - | 같은 입력을 로컬에서 실행한 값과 응답이 같음 |
| 잘못된 입력 | 422 + 틀린 항목과 이유 | 입력 검증 규칙 (`column-roles.json`의 범위) | 422 확인 후 올바른 값으로 200 |
| 모델 준비 실패 | 503 또는 서버 시작 실패 | 모델 경로·파일 해시 확인, 복원 또는 재학습 | `/health` 정상, 같은 입력 예측값이 이전과 같음 |
| 응답 성공·예측 오차 큼 | 200 (정상처럼 보임) | 입력 정보 부족·예보 오차 → 입력 추가 후 재학습 | 실제 대여 기록과 비교한 MAE, 평일 출퇴근 시간 MAE |

## 수업 중 추가 계산·판단

- 실제 10·20·30초, 예상 14·18·36초: 차이 크기 4·2·6초, MAE(평균절대오차) 4초. 12초와 4초가 각각 무엇을 뜻하나요? 
-> 12초는 세 문항 오차의 합계이고, 4초는 한 문항당 평균적으로 틀린 크기(MAE)임
- 학습 자료의 오차가 0초인 모델이 새 문항에서 7초, 다른 모델이 2초 틀렸다면 어떤 결과를 기준으로 판단할까요? 
-> 새 문항 결과를 기준으로 판단해 2초 모델을 고른다. 학습 오차 0초는 학습 자료를 외운 과적합일 수 있음.
- 상태 200, 예상 31.2초, 응답 대기 0.1초, 실제 50초: 예측 오차 18.8초. 빠른 응답과 정확한 예측은 같은 뜻인가요? 
-> 아니다. 0.1초는 답이 빨리 왔다는 뜻이고, 18.8초는 답이 얼마나 틀렸는지임.
- 입력 5건 중 실패 1건을 지우면 처리 대상은 4건입니다. 실패 입력을 수정하는 것과 어떤 차이가 있나요?
-> 지우면 원래 요청 1건이 처리되지 않고 사라짐. 수정하면 5건 모두 처리됨.
